# 构建与环境

本文说明本项目需要什么环境，怎么安装 MinGW，怎么构建，编译参数是什么，以及常见构建错误的处理办法。

本文的命令都在仓库根目录执行。

## 一 适用环境

| 项目 | 要求 |
| --- | --- |
| 操作系统 | Windows 10 或 Windows 11，64 位 |
| 编译器 | 64 位 MinGW-w64 GCC，支持 C++20 |
| C++ 标准 | `gnu++20` |
| 图形库 | 仓库自带 EasyX 静态库，不需要额外安装 |
| 测试脚本 | Windows PowerShell 5.1 或更高版本，脚本编码为 UTF-8 BOM |
| 文档工具 | 可选，VS Code 或 Obsidian |

本项目在 `g++ 16.2.0` 上测试通过。

代码用到了 C++20 的 `<format>`。这个特性从 GCC 13 开始可用。建议使用 GCC 13 或更高版本。版本太低会编译失败。

## 二 安装 MinGW-w64

### 2.1 下载

可以从下面两个地址下载：

- <https://github.com/niXman/mingw-builds-binaries/releases>
- <https://winlibs.com/>

选择版本时注意：

1. 必须选 64 位版本。文件名或说明里应当有 `x86_64` 或 `x86_64-w64-mingw32`。
2. 必须包含 `g++`。只含 `gcc` 的包不够。
3. 选 release 版本，不要选 debug 版本。
4. UCRT 与 MSVCRT 两种运行时都可以。拿不准时选 UCRT。
5. 建议选 GCC 13 以上版本。推荐直接用 16.2.0 附近的版本。

niXman 的压缩包名字类似：

```text
x86_64-16.2.0-release-posix-seh-ucrt-rt_v13-rev0.7z
```

winlibs 的压缩包名字里通常带 `winlibs-x86_64`。

### 2.2 解压

1. 解压到固定目录，例如 `D:\mingw64`。
2. 路径不要有中文，不要有空格。不要放在 `C:\Program Files`。
3. 打开解压后的目录，确认有 `bin` 文件夹。
4. 打开 `bin` 文件夹，确认有 `g++.exe`、`gcc.exe`、`objdump.exe`。

常见错误：

- 解压出双层 `mingw64\mingw64\bin`。这时 PATH 应当指向真正含 `g++.exe` 的 `bin` 目录。
- 只解压了一部分文件。重新解压完整压缩包。

### 2.3 配置 PATH

1. 按 `Win + S`，输入 `环境变量`。
2. 选择 `编辑系统环境变量`。
3. 点 `环境变量`。
4. 在 `系统变量` 里选中 `Path`，点 `编辑`。
5. 点 `新建`，填写 MinGW 的 `bin` 完整路径，例如 `D:\mingw64\bin`。
6. 点 `确定`，再点 `确定`，再点 `确定`。
7. 关闭全部已经打开的命令行窗口。

旧命令行窗口不会自动读取新的 PATH。必须重新打开。

如果双击 `build.bat` 时仍然找不到编译器，先打开一个新的命令行窗口运行一次。资源管理器有时需要重启才能拿到新的环境变量。

### 2.4 验证

打开新的命令行窗口，运行：

```bat
g++ --version
```

再运行：

```bat
gcc --version
```

正常输出类似：

```text
g++ (x86_64-win32-seh-rev0, Built by MinGW-Builds project) 16.2.0
```

还可以检查路径：

```bat
where g++
```

正常时第一行就是 MinGW 的 `g++.exe` 路径。

三个命令都正常，说明编译环境已经可用。

## 三 测试用的 PowerShell

本机默认使用 Windows 自带的 Windows PowerShell 5.1。测试脚本已经兼容 5.1，不需要安装 PowerShell 7。

运行测试的命令：

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File tests\run_tests.ps1
```

参数说明：

| 参数 | 作用 |
| --- | --- |
| `powershell` | Windows 自带的 Windows PowerShell 5.1 |
| `-NoProfile` | 不加载个人配置，避免环境差异 |
| `-ExecutionPolicy Bypass` | 只对本次运行放宽脚本执行策略 |
| `-File` | 指定要运行的脚本路径 |

如果已经安装了 PowerShell 7，也可以改用：

```pwsh
pwsh -File tests\run_tests.ps1
```

### 3.1 UTF-8 BOM 要求

测试脚本必须保存为 UTF-8 BOM 编码。

原因：

- Windows PowerShell 5.1 读取没有 BOM 的 UTF-8 文件时，会按系统 ANSI 代码页解码。
- 脚本里有中文注释和中文字符串，按 ANSI 解码会乱码，甚至导致语法错误。

保存方法：

1. 用 VS Code 打开 `tests\run_tests.ps1`。
2. 点右下角的编码按钮，选择 `通过编码保存`。
3. 选择 `UTF-8 with BOM`。
4. 保存后文件开头三个字节应为 `EF BB BF`。

### 3.2 安装 PowerShell 7（可选）

如果确实需要 PowerShell 7，可以用 winget 安装：

```bat
winget install --id Microsoft.PowerShell --source winget
```

也可以从 GitHub 下载安装包：

<https://github.com/PowerShell/PowerShell/releases>

安装后打开新命令行，检查：

```pwsh
pwsh --version
```

能显示版本号即可。

## 五 build.bat 流程

`build.bat` 是根目录的一键构建脚本。双击即可运行。

脚本做的事：

1. 切换到脚本所在目录。这样在任何位置调用都能找到仓库文件。
2. 解析参数。只有 `--no-pause` 有作用。
3. 打印标题。
4. 用 `where g++` 检查编译器。
   - 找不到时跳到 `:no_compiler`，打印英文下载提示，退出码 1。
5. 打印 `[1/3] Check compiler`，执行 `g++ --version`。
6. 打印 `[2/3] Build serve.exe`。
   - 先删除旧的 `serve.exe`。
   - 调用 g++ 编译全部源文件。
   - 编译失败或没有生成 `serve.exe` 时跳到 `:build_fail`，退出码 1。
   - 成功时打印 `[OK] serve.exe built`。
7. 打印 `[3/3] Build sample players`。
   - 依次检查 `battle\example\build.bat`、`battle\demo_expand\build.bat`、`battle\demo_random\build.bat`、`battle\demo_rush\build.bat`。
   - 存在就调用对应构建脚本，并传入 `--no-pause`。
   - 缺失时打印警告并标记 `AI_FAIL=1`。
   - 失败时打印警告并标记 `AI_FAIL=1`。
8. 打印构建结果和运行命令示例。
9. 有失败玩家时打印 `[TIP]`。
10. 默认执行 `pause`。加了 `--no-pause` 时直接退出。

退出码：

| 退出码 | 含义 |
| --- | --- |
| 0 | 主程序构建成功，示例玩家可能有失败 |
| 1 | 找不到编译器，或主程序构建失败 |

注意：示例玩家构建失败不会让 `build.bat` 返回 1。脚本只打印警告。多人模式可能因此无法运行。

## 六 编译参数逐项解释

主程序编译命令：

```bat
g++ -std=gnu++20 -finput-charset=UTF-8 -fexec-charset=UTF-8 -static -O2 -Wall -Wextra -Wno-unknown-pragmas -Wno-unused-parameter -Isrc -Ilib -o serve.exe src\main.cpp src\core\*.cpp src\io\*.cpp src\ui\*.cpp -Llib\easyx\lib -leasyx -lgdi32 -lole32 -lwinmm -lgdiplus
```

逐项说明：

| 参数 | 作用 |
| --- | --- |
| `g++` | 调用 C++ 编译器 |
| `-std=gnu++20` | 使用 C++20 标准，并允许 GNU 扩展 |
| `-finput-charset=UTF-8` | 告诉编译器源文件是 UTF-8 编码 |
| `-fexec-charset=UTF-8` | 让程序内的字符串字面量使用 UTF-8 编码 |
| `-static` | 静态链接 GCC 运行时、标准库和线程库 |
| `-O2` | 开启常用优化，提高运行速度 |
| `-Wall` | 打开常用警告 |
| `-Wextra` | 打开额外警告 |
| `-Wno-unknown-pragmas` | 忽略未知 `#pragma` 警告。EasyX 头文件里有 `#pragma comment` |
| `-Wno-unused-parameter` | 忽略未使用参数警告 |
| `-Isrc` | 把 `src` 加入头文件搜索路径 |
| `-Ilib` | 把 `lib` 加入头文件搜索路径 |
| `-o serve.exe` | 指定输出文件名 |
| `src\main.cpp` | 主入口 |
| `src\core\*.cpp` | 全部核心逻辑源文件 |
| `src\io\*.cpp` | 全部通信源文件 |
| `src\ui\*.cpp` | 全部界面源文件 |
| `-Llib\easyx\lib` | 把 EasyX 静态库目录加入链接搜索路径 |
| `-leasyx` | 链接 `libeasyx.a` |
| `-lgdi32` | 链接 Windows GDI 图形库 |
| `-lole32` | 链接 Windows OLE 库 |
| `-lwinmm` | 链接 Windows 多媒体库 |
| `-lgdiplus` | 链接 Windows GDI+ 库 |

示例玩家的编译命令：

```bat
g++ -std=gnu++20 -O2 -static -finput-charset=UTF-8 -fexec-charset=UTF-8 -o example.exe example.cpp
```

示例玩家只用 C++ 标准库。不需要 EasyX，不需要额外系统库。

## 七 EasyX 静态库说明

EasyX 的文件位置：

| 文件 | 说明 |
| --- | --- |
| `lib/easyx/easyx.h` | 主头文件 |
| `lib/easyx/graphics.h` | 图形接口头文件 |
| `lib/easyx/lib/libeasyx.a` | 静态链接库 |

链接时需要加：

```text
-Llib/easyx/lib -leasyx -lgdi32 -lole32 -lwinmm -lgdiplus
```

说明：

1. `libeasyx.a` 是静态库。链接后代码会进入 `serve.exe`。
2. 运行时不依赖 EasyX 的 DLL。
3. `-lgdi32`、`-lole32`、`-lwinmm`、`-lgdiplus` 是 Windows 系统库，系统自带，不属于外部运行时依赖。
4. EasyX 头文件里有 `#pragma comment`。MinGW 不认识这种写法，会出警告。`-Wno-unknown-pragmas` 用来关闭这个警告。
5. 不需要单独安装 EasyX，也不需要配置系统环境变量。

官方网址：<https://easyx.cn>

如果链接时报找不到 EasyX 函数，先确认命令在仓库根目录执行，再确认 `lib/easyx/lib/libeasyx.a` 存在。

## 八 静态链接验证

本项目要求运行时不依赖 MinGW 的动态库。验证方法如下。

### 8.1 用 objdump 查看依赖

在仓库根目录运行：

```bat
objdump -p serve.exe | findstr /C:"DLL Name"
```

如果 `objdump` 不在 PATH，可以用完整路径：

```bat
D:\mingw64\bin\objdump.exe -p serve.exe | findstr /C:"DLL Name"
```

正常时只会看到 Windows 系统 DLL，例如：

```text
DLL Name: KERNEL32.dll
DLL Name: USER32.dll
DLL Name: GDI32.dll
DLL Name: ADVAPI32.dll
DLL Name: SHELL32.dll
DLL Name: ole32.dll
DLL Name: winmm.dll
DLL Name: gdiplus.dll
```

使用 MSVCRT 运行时的 MinGW 还会看到：

```text
DLL Name: msvcrt.dll
```

使用 UCRT 运行时的 MinGW 还会看到：

```text
DLL Name: ucrtbase.dll
DLL Name: api-ms-win-crt-heap-l1-1-0.dll
DLL Name: api-ms-win-crt-runtime-l1-1-0.dll
...
```

这些也是 Windows 系统自带的组件，不算 MinGW 动态库。

### 8.2 不能出现的内容

如果看到下面任意一个，说明没有静态链接成功：

```text
libstdc++-6.dll
libgcc_s_seh-1.dll
libgcc_s_dw2-1.dll
libwinpthread-1.dll
```

处理办法：

1. 确认编译命令里有 `-static`。
2. 确认使用的 `g++.exe` 是 MinGW 的，不是 MSYS2 或其他环境里的。
3. 重新运行 `build.bat`。

### 8.3 验证程序能启动

```bat
serve.exe --help
```

能打印帮助信息，说明程序可以启动。

再运行一局无界面模式：

```bat
serve.exe --config config\example.json --no-ui
```

能正常结束并打印排名，说明运行环境正常。

## 九 从干净状态构建

1. 关闭正在运行的 `serve.exe`。
2. 关闭可能占用 `serve.exe` 的窗口。
3. 删除根目录的 `serve.exe`。
4. 运行：

```bat
build.bat --no-pause
```

5. 看到 `[OK] serve.exe built` 表示主程序成功。
6. 看到全部示例玩家 `[OK] player xxx built` 表示示例玩家成功。
7. 检查根目录是否生成 `serve.exe`。
8. 检查 `battle/example/example.exe` 是否存在。

如果只是改了 `src` 下的代码，重新运行 `build.bat` 即可。

如果改了 `build.bat` 本身，也要重新运行。

## 十 常见构建错误与解决办法

### 10.1 找不到 g++

现象：

```text
[ERROR] g++ compiler not found.
```

或者：

```text
'g++' 不是内部或外部命令，也不是可运行的程序
```

原因：MinGW 没装好，或者 PATH 没配好。

处理：

1. 确认 MinGW 已经解压。
2. 确认 `D:\mingw64\bin\g++.exe` 存在。
3. 确认 PATH 里有 `D:\mingw64\bin`。
4. 关闭旧命令行窗口，重新打开。
5. 运行 `where g++` 验证。

### 10.2 改了 PATH 仍然找不到

原因：旧窗口缓存了旧环境变量，或者 PATH 加错了位置。

处理：

1. 全部命令行窗口关闭，重新打开。
2. 开始菜单搜索 `cmd`，打开新窗口。
3. 运行 `echo %PATH%`，检查是否包含 MinGW 的 bin。
4. 检查 PATH 里是否有中文路径或多余引号。
5. 检查是否把 `D:\mingw64` 写成了 `D:\mingw64\bin\g++.exe`。PATH 要填目录，不是文件。

### 10.3 找不到头文件

现象：

```text
fatal error: include/type.hpp: No such file or directory
```

原因：没有在仓库根目录运行，或者缺少 `-Isrc`。

处理：

1. 确认当前目录是仓库根目录。
2. 确认 `src/include/type.hpp` 存在。
3. 用 `build.bat` 构建，它会自动加 `-Isrc -Ilib`。

### 10.4 找不到 EasyX 库

现象：

```text
cannot find -leasyx
```

原因：库路径不对，或者 `libeasyx.a` 不存在。

处理：

1. 确认当前目录是仓库根目录。
2. 确认 `lib\easyx\lib\libeasyx.a` 存在。
3. 确认命令里有 `-Llib\easyx\lib`。
4. 用 `build.bat` 构建。

### 10.5 EasyX 函数未定义

现象：

```text
undefined reference to `initgraph'
undefined reference to `SetWindowTextA'
```

原因：链接参数顺序不对，或者缺少 Windows 系统库。

处理：

1. 调整参数顺序。库参数放在源文件后面。
2. 确认有 `-leasyx -lgdi32 -lole32 -lwinmm -lgdiplus`。
3. 用 `build.bat` 构建，不要手写简化命令。

### 10.6 找不到 std::format

现象：

```text
error: 'format' is not a member of 'std'
```

原因：GCC 版本太低。`<format>` 从 GCC 13 开始支持。

处理：

1. 运行 `g++ --version` 查看版本。
2. 升级到 GCC 13 或更高版本。
3. 重新配置 PATH。

### 10.7 logo 或 `#pragma comment` 警告

现象：

```text
warning: ignoring '#pragma comment '
```

原因：EasyX 头文件里的 MSVC 专用写法。

处理：这是预期警告。`build.bat` 已经用 `-Wno-unknown-pragmas` 关闭。可以忽略。

### 10.8 无法删除 serve.exe

现象：

```text
cannot open output file serve.exe: Permission denied
```

原因：程序正在运行，或者被杀毒软件占用。

处理：

1. 关闭所有 `serve.exe` 窗口。
2. 打开任务管理器，结束 `serve.exe` 进程。
3. 重新运行 `build.bat`。
4. 如果杀毒软件拦截，把仓库目录加入信任列表。

### 10.9 字符编码错误

现象：

```text
cc1plus: error: bad value 'UTF-8' for '-fexec-charset'
```

或者中文显示乱码。

原因：编译器版本太旧，或命令行代码页不对。

处理：

1. 升级 MinGW 到支持 UTF-8 选项的版本。
2. 用 `chcp 65001` 把命令行切到 UTF-8。
3. 用 Windows Terminal。
4. `build.bat` 的提示本来就是英文，避免编码问题。

### 10.10 程序启动后立刻退出

原因：配置错误、日志目录不可写、`battle` 目录下没有可用玩家。

处理：

1. 打开命令行运行，观察错误信息。
2. 检查 `config/example.json` 是否存在。
3. 检查 `logs` 目录是否可写。
4. 检查 `battle/example/example.exe` 是否存在。
5. 先运行 `build.bat` 构建示例玩家。

### 10.11 示例玩家构建失败

现象：

```text
[WARN] player example build failed
```

处理：

1. 进入 `battle/example` 目录。
2. 双击 `build.bat`，查看具体编译错误。
3. 检查编译器是否可用。
4. 检查源码是否存在。
5. 解决后回到根目录重新运行 `build.bat`。
